## 1. 文档目的

这份文档用于把 `阿财` 项目从“文档和静态原型阶段”推进到“可开发、可联调、可验收”的执行状态。

这份文档主要回答以下问题：
- 当前研发起点是什么
- V1 应按什么顺序推进
- 每个阶段的产出物是什么
- 哪些事项现在必须做，哪些事项暂时不要做
- 什么情况下可以进入联调、测试和上线准备

说明：
- PRD 继续负责产品约束
- 技术方案继续负责系统设计
- 本文档只负责研发推进顺序、阶段目标和交付节奏

## 2. 当前项目基线

截至 2026-04-14，项目已具备以下基础：

- 产品边界已基本定稿
- 页面结构已基本定稿
- 四种业务状态已定稿
- 外部接口协议已成文
- Worker 内部 Structured Outputs 契约已成文
- 数据库存储方案和首版 migration 已写出
- 静态原型页已存在

当前仍未完成的关键事项：

- 还没有正式前端工程脚手架
- 还没有正式 Worker 工程脚手架
- 还没有共享的 TypeScript 契约层
- 还没有实际 Responses API 调用代码
- 还没有 Supabase 写库链路验证
- 还没有前后端联调闭环

因此，项目当前阶段不再是“继续讨论产品形态”，而是“把既有文档转成工程实现”。

## 3. 开发目标

V1 开发期的目标是交付一个最小可运行闭环，满足以下条件：

- 用户可以完成介绍页、表单页、结果页的完整主流程
- Worker 能稳定返回 4 种固定业务状态之一
- 规则不通过时不会触发联网分析
- 联网分析必须按轮次升级，而不是一次大搜索
- 候选结果必须携带可点击来源链接
- 系统必须保留匿名问答记录，支持后续复盘
- 前端只做展示和交互，不自行推断业务状态

## 4. V1 完成标准

满足以下条件时，可以认为 V1 达到“可联调完成、可进入上线准备”：

1. `POST /api/v1/analyze` 已可稳定返回固定结构 JSON
2. 四种业务状态都能通过真实接口返回，不依赖前端本地假数据
3. 规则拦截路径、搜索路径、搜索降级路径都已覆盖
4. 候选场景下每只股票都有独立置信度和来源列表
5. 来源链接为真实可点击链接，而不是纯文案标签
6. `analysis_records`、`analysis_candidates`、`candidate_evidence` 写入链路可用
7. 单元测试、集成测试和前端验收测试具备最小覆盖
8. 日志、错误码、超时和降级策略有基本保障

## 5. 开发原则

### 5.1 契约先行

- 先把接口结构、状态枚举、schema 常量和 mock 数据定死
- 再开始前后端并行开发

### 5.2 Worker 统一仲裁

- Worker 负责输入校验、规则判断、模型编排、证据门槛和最终结果组装
- 前端不能复制后端投资逻辑

### 5.3 先闭环，再增强

- 先做最小可运行链路
- 再补充性能优化、缓存、细化文案和更完整监控

### 5.4 证据优先

- 证据不足时宁可不给明确候选
- 不允许为了“看起来有结果”而降低来源门槛

### 5.5 控制范围

V1 不额外扩展以下内容：

- 登录注册
- 用户历史记录页
- 收藏和分享
- 实时行情联动
- 多轮对话
- 复杂运营后台

## 6. 建议研发节奏

建议把 V1 切成 6 个阶段推进。

如果是 1 名前端 + 1 名后端并行推进，建议总周期为 3 到 5 周。

如果主要由 1 人串行推进，建议按阶段交付，不承诺固定自然周上线时间，以避免因为模型编排和数据库联调低估工作量。

## 7. 阶段计划

### 7.1 Phase 0：项目启动与基线冻结

目标：
- 把“文档约束”转成“工程约束”
- 搭出正式开发骨架

核心任务：
- 确定正式工程目录结构
- 确定前端技术栈和包管理方式
- 确定 Worker 项目初始化方式
- 整理环境变量、密钥和本地开发说明
- 冻结共享枚举、字段命名和 mock 数据规范
- 建立 lint、format、test 的基础命令

交付物：
- 正式项目脚手架
- README 或开发启动说明
- 环境变量清单
- 共享字段与状态枚举定义草案

完成标志：
- 前端和 Worker 都可以本地启动
- 团队对目录结构和命名不再反复讨论

### 7.2 Phase 1：接口契约与骨架落地

目标：
- 把文档中的接口定义和内部 schema 转成代码资产

核心任务：
- 基于 `api-contract-v1.md` 生成 TypeScript 类型
- 基于接口协议补充 Zod 或等价校验定义
- 基于 `responses-schemas-v1.md` 生成 Worker 内部 schema 常量
- 建立共享状态枚举、错误码枚举和 mock 响应
- 搭建 Worker 的 `/api/v1/analyze` 路由骨架
- 统一错误处理中间件和响应包装方式

交付物：
- `shared/contracts` 或等价目录
- 请求与响应类型定义
- 业务状态枚举、错误码枚举
- Worker 路由骨架和 mock 返回

完成标志：
- 前后端都依赖同一套契约
- `/api/v1/analyze` 已能返回固定结构 mock 数据

### 7.3 Phase 2：规则引擎与本地闭环

目标：
- 不依赖模型先跑通“提交 -> 规则判断 -> 固定结果 -> 写库”

核心任务：
- 实现请求规范化
- 实现信息不足判断
- 实现目标偏高判断
- 实现条件冲突判断
- 实现业务状态映射与 `status_label` 映射
- 实现结果组装器
- 打通 `analysis_records` 写入
- 在规则拦截路径下返回真实固定结构结果

交付物：
- Rule Engine 模块
- Result Composer 模块
- 首条真实数据库写入链路
- 规则拦截场景测试用例

完成标志：
- 规则不通过时不触发模型调用
- `INSUFFICIENT_INFO` 和 `TARGET_TOO_HIGH_OR_CONFLICT` 两类结果可真实返回

### 7.4 Phase 3：Responses Pipeline 与证据门槛实现

目标：
- 跑通“规则通过 -> 分轮搜索 -> 证据校验 -> 最终结果”的核心链路

核心任务：
- 实现 Round 1 到 Round 3 的分轮调用
- Round 4 仅作为背景补充，不进入核心候选判定
- 建立 Candidate Narrowing 调用
- 建立 Evidence Verification 调用
- 建立 Structured Assessment 调用
- 对每轮模型输出进行 schema 校验
- 建立来源级别映射、去重和证据标准化
- 实现 Evidence Gatekeeper
- 实现候选、证据和轮次日志写库

交付物：
- Responses Orchestrator
- Prompt 模板与 schema 校验逻辑
- 候选与证据写库流程
- 轮次日志记录结构

完成标志：
- `NO_CLEAR_CANDIDATES` 和 `HAS_CANDIDATES` 两类结果可真实返回
- Worker 能根据证据充分性决定是否升级轮次
- 模型不直接输出最终自由文本结果

### 7.5 Phase 4：前端集成与交互完成

目标：
- 把静态原型转换为真实可联调页面

核心任务：
- 接入正式路由和页面结构
- 把 Google Stitch 产物整理为可维护组件
- 接入表单状态管理和提交流程
- 接入结果页四种状态渲染
- 实现条件摘要渲染
- 实现候选卡片、置信度展示和证据展开区
- 实现来源链接跳转
- 实现加载态、错误态和回到表单重编辑流程

交付物：
- 可运行前端页面
- 真实 API 调用层
- 四状态联调页面

完成标志：
- 首页、表单页、结果页职责边界清晰
- 前端不再依赖手写假数据演示完整流程

### 7.6 Phase 5：测试、观测与上线准备

目标：
- 为交付和后续迭代建立最低质量保障

核心任务：
- 补齐规则引擎单元测试
- 补齐结果结构组装测试
- 补齐接口集成测试
- 补齐前端主流程验收测试
- 校验 migration 执行和回滚方案
- 建立关键日志字段和流程埋点
- 确认超时、降级和错误码展示策略
- 编写最小发布说明和回归清单

交付物：
- 单元测试、集成测试、验收测试
- 观测字段清单
- 发布与回归清单

完成标志：
- 四类结果、规则拦截、搜索降级路径都有测试覆盖
- 团队可以进行一次完整的预发布验收

## 8. 里程碑定义

建议设置以下 5 个里程碑：

1. M1：工程骨架建立完成
   - 前后端项目都可启动
   - 契约命名达成一致

2. M2：接口与 mock 联调完成
   - `/api/v1/analyze` 返回固定结构 mock 数据
   - 前端能渲染四种结果状态

3. M3：规则引擎闭环完成
   - 规则拦截路径真实可用
   - `analysis_records` 写入成功

4. M4：真实分析闭环完成
   - Responses Pipeline、证据门槛和结果组装真实可用
   - 候选与证据数据可落库

5. M5：验收与上线准备完成
   - 测试通过
   - 风险项可控
   - 可以进入灰度或首发准备

## 10. 关键依赖与前置条件

以下事项建议在 Phase 1 之前确认或至少占位：

- OpenAI API Key
- Cloudflare Worker 开发与部署账号
- Supabase 项目与连接信息
- Hyperdrive 配置方式
- 本地开发环境说明
- Google Stitch 初版页面可复用程度

说明：
- 这些事项可以先用占位值或本地环境变量推进，不必全部完成后才启动编码
- 但至少要保证工程结构和契约层不被这些不确定项阻塞

## 11. 当前不阻塞开发但需要记录的待确认项

以下事项可以并行确认，但不应阻塞 Phase 0 到 Phase 2：

- 前端最终采用 SSR 还是纯前后端分离
- Responses API 各阶段最终使用的模型型号
- 是否增加搜索结果缓存层
- 结果页是否保留分数和等级双展示
- 表单页是否支持结果页回填编辑
- 证据展开区最终交互细节

处理原则：
- 先留扩展点
- 不因这些问题停下主链路开发

## 12. 主要风险与应对

### 12.1 风险一：模型输出不稳定

风险：
- Structured Outputs 虽然约束更强，但仍可能出现字段缺失、证据不足或不满足业务门槛

应对：
- 每轮调用后都做 schema 校验
- Worker 做最终仲裁，不直接信任模型
- 不满足门槛时升级轮次或返回无明确候选

### 12.2 风险二：联网分析耗时偏长

风险：
- 多轮调用会带来整体响应时间上升

应对：
- 明确前端分析中状态
- 设定超时与降级策略
- 先优化轮次停止条件，再考虑缓存

### 12.3 风险三：来源质量不够稳定

风险：
- 某些轮次可能搜不到足够的一二三级证据

应对：
- 严格执行来源优先级
- 证据不足时输出 `NO_CLEAR_CANDIDATES`
- 不为了给结果而降低标准

### 12.4 风险四：数据链路联调延迟

风险：
- Supabase、Hyperdrive、Worker 三者联调容易拖慢节奏

应对：
- 先实现内存 mock 和结果闭环
- 再替换为真实写库
- 先打通主表写入，再补候选和证据表

### 12.5 风险五：范围蔓延

风险：
- 很容易在 V1 中继续扩张页面、记录、行情、推荐等能力

应对：
- 所有新增需求先对照 PRD 和交接文档
- 非 V1 核心能力一律进入后续版本池

## 13. 推荐的立即执行动作

如果现在就开始推进，建议按以下顺序执行：

1. 建正式工程骨架
2. 生成共享 TypeScript 类型和校验定义
3. 建 `/api/v1/analyze` 路由骨架
4. 跑通规则引擎和固定结果结构
5. 验证 Supabase migration 与写库链路
6. 接入 Responses Pipeline 分轮逻辑
7. 完成前端真实联调
8. 补测试、日志和发布清单

## 14. 建议的首个开发里程碑

当前最值得优先达成的不是“页面更好看”，而是下面这个里程碑：

“接口契约代码化，并让 Worker 返回可联调的固定结构结果。”

原因：
- 这是前后端并行开发的分界点
- 这是后续规则引擎、模型编排和结果页渲染的共同基础
- 这一步完成后，项目就从“文档项目”正式进入“工程项目”

## 15. 结论

`阿财` 项目当前最合理的推进方式，不是继续扩展产品讨论，而是围绕“契约先行、Worker 仲裁、分轮搜索、证据优先、先闭环再增强”五条原则，分阶段落地。

建议优先完成：

1. 工程骨架
2. 契约代码化
3. Worker 骨架
4. 规则闭环
5. Responses Pipeline
6. 前端联调
7. 测试与上线准备

只要按这个顺序推进，项目就能较稳定地从当前文档状态过渡到一个可交付的 V1。
