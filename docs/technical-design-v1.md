## 1. 文档目的

这份文档用于在设计稿未完全定稿前，先明确 `阿财` V1 的技术实现边界、系统结构、接口约束、数据流、风险控制和研发拆分方式。

目标不是一次性写完所有实现细节，而是先回答以下问题：
- V1 具体要做哪些能力
- 这些能力如何拆成前端、后端和规则判断模块
- 哪些技术点已经可以先定
- 哪些内容需要等设计稿或数据源策略进一步确认

## 2. 项目背景

`阿财` 是一个基于公开信息的 A 股候选股票筛选与研读辅助工具。

产品核心流程为：
1. 用户进入介绍页理解产品边界
2. 用户在表单页填写投资条件
3. 系统先做本地规则判断
4. 只有规则通过时才进入联网搜索与来源筛选
5. 系统返回 4 种固定结果状态之一
6. 结果页按结构化方式展示原因、候选和来源证据

技术设计必须贯彻以下产品原则：
- 先规则判断，再联网搜索
- 优先证据，不优先迎合用户
- 证据不足时宁可不给明确候选
- 输出结构固定，避免自由发挥

## 3. 设计范围

### 3.1 V1 范围内

- 介绍页、表单页、结果页三个独立页面形态
- 条件输入、前端校验、结果页回显
- 本地规则判断
- 联网搜索触发控制
- 来源分级与候选证据组织
- 固定结构结果输出
- 结果页四种状态的统一承载
- 匿名会话与问答记录留痕

### 3.2 V1 不在范围内

- 登录注册
- 用户账户体系
- 历史记录
- 收藏和分享
- 实时行情联动
- 投资组合管理
- 多轮对话

## 4. 当前需要先定的技术结论

设计稿还没有完全出完，但以下内容建议现在就定下来：

### 4.1 系统边界

- 前端只负责输入、展示、交互反馈，不负责投资逻辑判断
- 后端统一负责规则判断、联网检索、来源筛选和结果组装
- 所有业务结果必须从后端返回，前端不自行拼接候选结论

### 4.2 状态模型

系统只允许返回以下 4 个业务状态：
- `信息不足`
- `目标偏高或条件冲突`
- `暂无明确候选`
- `已有候选`

前后端围绕这 4 个状态做枚举和分支，不新增临时状态名。

### 4.3 流程闸门

联网搜索必须满足以下前提：
- 必填字段完整
- 目标收益未明显偏高
- 条件不存在明显冲突

也就是说，规则引擎是搜索引擎前的硬闸门，而不是提示性质的软建议。

### 4.4 结果组织方式

- 结果页必须展示本次用户已选条件摘要
- 每只候选股票必须单独成块
- 每只候选必须有自己的置信度
- 每只候选必须有自己的来源证据展开区
- 不允许做页面级统一证据池替代个股证据

### 4.5 当前技术选型

- 前端 UI 由 Google Stitch 生成初版界面
- 前端工程实现与联调由 Codex 完成
- 后端采用 Cloudflare Worker 作为统一编排层
- 模型调用采用 OpenAI Responses API
- 联网检索优先使用 Responses API 内置 `web_search`
- 数据库存储采用 Supabase Postgres
- Worker 与 Supabase 之间通过 Hyperdrive 连接
- 结果最终由 Worker 输出为固定结构 JSON，前端只负责渲染

## 5. 目标架构

建议 V1 按以下逻辑模块设计：

1. `Web Client`
   - 承载介绍页、表单页、结果页
   - 负责表单交互、提交、加载态、错误态、结果展示
2. `Worker Orchestrator`
   - 接收筛选请求
   - 做输入校验
   - 运行在 Cloudflare Worker
   - 编排规则引擎、Responses API 分阶段调用和结果组装
3. `Rule Engine`
   - 判断信息是否完整
   - 判断目标收益是否明显偏高
   - 判断条件是否明显冲突
4. `Responses Pipeline`
   - 在规则通过后执行分轮次候选缩小和证据提取
   - 每个阶段都要求结构化 JSON 输出
   - 联网搜索默认使用 `web_search` 工具
5. `Evidence Gatekeeper`
   - 将不同来源整理成统一证据结构
   - 做来源级别标记、去重和冲突校验
   - 校验候选是否真的满足输出门槛
6. `Result Composer`
   - 统一输出 4 类结果结构
   - 生成候选摘要、风险、不确定性、来源证据列表
7. `Storage Layer`
   - 采用 Supabase Postgres 持久化匿名会话、问答记录、轮次日志和证据引用
   - 由 Worker 写入，不对前端开放数据库直连

## 6. 端到端流程

### 6.1 用户主流程

1. 用户进入介绍页
2. 用户跳转到表单页并填写条件
3. 前端完成基础格式校验
4. 前端向 Worker 发起分析请求
5. Worker 执行规则引擎
6. 若规则不通过，直接返回 `信息不足` 或 `目标偏高或条件冲突`
7. 若规则通过，Worker 分阶段调用 Responses API
8. Worker 对模型产出做后置校验和结果组装
9. 前端跳转结果页并按状态渲染

### 6.2 建议的后端链路

建议后端按以下顺序实现：

1. Worker 接收表单请求并做输入校验
2. Worker 执行本地规则校验
3. 若规则未通过，直接返回固定业务状态，不调用模型
4. 若规则通过，Worker 分阶段调用 Responses API
5. 每次模型调用都要求返回结构化 JSON，不让模型直接自由写最终文案
6. Worker 对候选、来源级别和证据条目做后置校验
7. 只有满足来源门槛的候选才允许进入最终结果
8. Worker 统一组装最终响应 JSON
9. 前端只按 4 种固定状态渲染

### 6.3 状态机建议

- `idle`：未提交
- `editing`：编辑表单
- `submitting`：提交中
- `succeeded`：成功返回业务结果
- `failed`：接口或系统异常

说明：
- `failed` 只表示系统调用失败，不对应业务结果状态
- 业务状态和请求状态必须分离，避免混淆

### 7.1 页面拆分

- `/`：介绍页
- `/form`：表单页
- `/result`：结果页

### 7.2 前端模块建议

- `IntroPage`
- `FilterFormPage`
- `ResultPage`
- `ConditionSummary`
- `ResultStatusBanner`
- `CandidateCard`
- `EvidenceAccordion`
- `SourceLinkList`
- `RiskNotice`

### 7.3 前端职责

- 控制页面跳转和加载态
- 管理表单状态
- 做必填与格式层面的即时反馈
- 对后端返回结果进行纯展示渲染

### 7.4 前端不要承担的职责

- 不在前端复制一套投资规则引擎
- 不在前端生成候选结论
- 不在前端根据文案猜测结果状态
- 不在前端拼接来源可信度判断

说明：
- 前端可以有轻量校验，但后端必须是最终判断来源

## 8. 输入模型设计

### 8.1 请求字段

建议接口输入结构如下：

```json
{
  "budget": 50000,
  "target_return_reference": 12,
  "risk_tolerance": "MAX_DRAWDOWN_10",
  "investment_cycle": "ONE_YEAR",
  "volatility_acceptance": false,
  "industry_preference": ["高股息", "家电", "出海制造"],
  "style_preference": "DIVIDEND"
}
```

### 8.2 字段设计原则

- 前端展示中文文案
- 接口传输使用稳定的英文代码值
- 后端统一做枚举映射
- 可选字段允许为空或默认值

### 8.3 前端校验范围

- 数字格式是否合法
- 必填项是否缺失
- 多选数量是否超限
- 搜索选择项是否命中合法候选

### 8.4 后端校验范围

- 枚举值是否合法
- 数值区间是否合法
- 必填字段是否完整
- 条件组合是否可判定

## 9. 规则引擎设计

### 9.1 规则引擎职责

规则引擎只做三类事：
- 信息完整性检查
- 目标收益合理性判断
- 条件冲突判断

### 9.2 规则输出建议

建议规则引擎输出统一结构：

```json
{
  "passed": false,
  "status": "TARGET_TOO_HIGH_OR_CONFLICT",
  "reasons": [
    "一年周期下 20% 以上目标收益偏高",
    "不接受高波动与当前收益目标存在冲突"
  ],
  "suggestions": [
    "将目标收益参考调整到 10% 至 15%",
    "或提高高波动接受度后再试一次"
  ]
}
```

### 9.3 规则维护建议

- 阈值表独立配置
- 冲突规则独立配置
- 高波动主题词表独立配置
- 规则实现与接口层解耦，便于后续扩展

## 10. 联网搜索与来源策略设计

### 10.1 搜索模块目标

搜索模块不是通用搜索，而是“带来源约束的候选验证流程”。

### 10.2 建议拆成“阶段 + 轮次”双层编排

建议不要打一枪式单次搜索，而是做成“固定阶段 + 分级轮次”的编排。

阶段建议如下：

1. `Candidate Narrowing`
   - 根据行业偏好、风格偏好、周期和风险特征缩小候选范围
   - 输出候选池和初步理由的结构化 JSON
2. `Evidence Verification`
   - 针对候选逐个补足公开信息证据
   - 输出来源级别、证据条目和候选支撑点的结构化 JSON
3. `Structured Assessment`
   - 基于已有证据输出候选判断、中间分析和待补充项
   - 不直接输出给用户看的最终自由文案

轮次建议如下：

1. `Round 1`
   - `allowed_domains` 只放一级来源
   - 目标是优先获取法定披露和官方事实源
2. `Round 2`
   - 仅当一级证据不足时才进入
   - `allowed_domains` 放一级 + 二级来源
3. `Round 3`
   - 仅当二级补充后仍不足时才进入
   - `allowed_domains` 放一级 + 二级 + 三级来源
4. `Round 4`
   - 四级来源只用于背景补充
   - 不参与核心候选结论成立与否的判定

说明：
- 轮次升级条件由 Worker 控制，不交给模型自由决定
- 每一轮都必须产出“证据是否充分、是否进入下一轮”的结构化字段

### 10.3 来源分级模型

- `L1`：法定披露和官方事实源
- `L2`：官方互动与路演平台
- `L3`：主流结构化行情和财务快查平台
- `L4`：主流财经新闻平台

### 10.4 搜索策略约束

- 优先从可信来源池开始
- 一级来源和其他来源冲突时以一级来源为准
- 缺少一级来源时，不轻易输出明确候选
- 新兴主题不能只靠概念热度输出候选
- 能用域名白名单时，优先用白名单而不是只靠提示词约束

### 10.5 失败降级策略

- 搜索失败时，不返回空白页
- 来源不足时，降级到 `暂无明确候选`
- 核心字段无法核实时，降级到 `信息不足` 或 `暂无明确候选`

### 10.6 Responses API 调用约束

- 每次调用都必须使用 Structured Outputs
- 在 Responses API 中通过 `text.format = { "type": "json_schema", ... }` 指定严格 JSON Schema
- 模型输出只承担“候选缩小、证据抽取、结构化判断”职责
- 最终面向前端的响应对象由 Worker 组装，不直接透传模型原文
- 若模型输出缺字段、来源不合法或状态不在枚举内，Worker 必须判为失败并降级
- 若模型给出候选但证据门槛不满足，Worker 必须剔除候选并重新判定状态
- 优先使用 `web_search`，仅在兼容性原因下才考虑 `web_search_preview`
- 不使用“纯文本格式约束”替代 Schema 校验

建议每轮最少包含以下 Schema 字段：

- `round`
- `allowed_source_levels`
- `candidate_pool`
- `evidence_items`
- `evidence_sufficient`
- `missing_evidence`
- `should_escalate_to_next_round`
- `proposed_status`

### 10.7 可信来源池处理建议

可信来源池建议分三层处理：

1. `Prompt Guidance`
   - 在系统提示词中明确要求优先查找 `cninfo.com.cn`、`sse.com.cn`、`szse.cn` 等可信站点
2. `Tool Filters`
   - 在 Responses API 的 `web_search` 工具中配置 `filters.allowed_domains`
   - 尽可能把搜索范围限制在可信来源池和必要的补充来源池内
3. `Worker Post Validation`
   - Worker 读取返回的来源列表
   - 对来源域名、来源级别和证据数量做二次过滤
   - 不满足门槛时降级为 `暂无明确候选` 或 `信息不足`

说明：
- 如果使用的是 `web_search_preview`，域名过滤能力和可控性会弱一些
- 当前方案更建议使用 `web_search` + `allowed_domains` + Worker 后置校验 的组合

### 10.8 Worker 后置仲裁规则

Worker 不只是“转发模型结果”，而是最终仲裁者。

至少要做以下后置判断：

- 候选是否具备达到当前状态所需的最低来源级别
- 候选是否存在足够数量的有效证据条目
- 证据链接域名是否落在允许范围内
- 四级来源是否被错误用于核心结论
- 候选数量是否超过上限
- 置信度等级是否与证据等级相匹配

若任一判断不通过：

- 剔除不合格候选
- 重新计算整体状态
- 必要时降级为 `暂无明确候选`

## 11. 结果模型设计

### 11.1 统一响应结构建议

```json
{
  "request_id": "uuid",
  "status": "HAS_CANDIDATES",
  "condition_summary": {},
  "analysis": {
    "reasons": [],
    "suggestions": [],
    "overall_note": ""
  },
  "candidates": [],
  "risk_notice": "仅供参考，不构成投资建议"
}
```

说明：
- 这个响应对象的最终责任方是 Worker
- 模型可以提供中间 JSON，但不能直接决定最终返回体
- 最终返回体中的引用链接必须保留，供前端渲染为可点击来源

### 11.2 候选结构建议

```json
{
  "stock_name": "美的集团",
  "stock_code": "000333",
  "industry": "家电",
  "selection_reason": "与中低波动、红利偏好的一年周期更匹配",
  "evidence_summary": "公开年报可验证现金流与分红连续性",
  "major_risks": "出口波动可能影响利润弹性",
  "uncertainties": "仍需确认后续需求与公司指引",
  "confidence": "HIGH",
  "confidence_score": 78,
  "primary_sources": ["L1", "L2"],
  "evidence_items": []
}
```

### 11.3 证据项结构建议

```json
{
  "source_level": "L1",
  "source_name": "巨潮资讯",
  "title": "2025 年年度报告",
  "url": "https://...",
  "publish_date": "2026-03-29",
  "snippet": "用于确认收入结构、经营现金流与分红延续性",
  "supports": ["分红稳定", "现金流较强"]
}
```

### 11.4 前端引用展示约束

- 如果前端展示了搜索结果或来源引用，链接必须清晰且可点击
- 候选卡片中不能只展示“一级/二级/三级”文字标签
- 每个候选至少应有独立的来源链接区或展开区
- 前端应优先展示模型实际引用到的链接，而不是只展示来源分类

## 12. 数据、配置与存储设计

V1 现在建议引入数据库，以支持后续复盘和质量迭代。

存储结论：

- 主数据库使用 Supabase Postgres
- Worker 通过 Hyperdrive 连接 Supabase
- 前端不直连数据库
- 问答记录写入数据库，但 V1 前端不展示历史记录

同时，以下内容仍应抽成配置层：

- 投资周期与收益阈值映射表
- 风险承受能力枚举表
- 风格偏好枚举表
- 高波动主题词表
- 可信来源池配置
- 结果状态映射表
- 风险声明模板

这样可以形成“数据库留痕 + 配置驱动规则”的实现，避免规则散落在页面和接口逻辑中。

## 13. 错误处理与降级

### 13.1 错误分类

- 用户输入错误
- 规则判断结果
- 外部来源访问失败
- 系统内部异常

### 13.2 处理原则

- 用户输入错误：前端即时提示
- 规则判断结果：按业务状态返回
- 外部来源失败：尽量降级为可解释结果
- 系统异常：返回统一错误页或错误提示，不伪造业务结论

## 14. 合规与风险控制

这是 V1 的重点章节，必须写。

至少要包含：
- 不提供确定性买卖建议
- 不承诺收益
- 不编造事实、数据和来源
- 不在无可验证依据时给出明确候选
- 风险声明固定出现在结果末尾
- 输出口径必须克制，不出现荐股式表达
- OpenAI API Key 只能放在 Worker 服务端，不进入前端代码和 Stitch 产物

## 15. 成本、权限与密钥要求

### 15.1 密钥使用要求

- OpenAI API Key 必须作为 Cloudflare Worker Secret 注入
- 前端不得直接持有 OpenAI Key
- 如使用项目级 API Key，需要确保该 Key 具备对应接口权限
- Supabase 数据库连接信息同样只能保存在 Worker 服务端
- 前端不得直接持有 Supabase service role 或数据库密码

### 15.2 权限检查重点

- Key 需要能调用 `/v1/responses`
- Key 需要能使用所选模型
- 若启用 web search，Key 对应项目还需要具备相关模型与工具访问能力

### 15.3 成本控制建议

- 将规则引擎前置，减少无效模型调用
- 采用“本地规则拦截 -> 分阶段搜索 -> 后置校验”的链路控制调用次数
- 对搜索阶段设置超时、候选上限和来源上限
- 埋点记录每次分析的模型调用次数与平均成本
- 数据库存储优先保留结构化摘要，避免无节制落全量原始大文本

## 16. 可观测性与日志

建议最少记录以下埋点与日志：

- 表单提交次数

- 来源抓取失败率

- 候选数量分布

日志中不要记录不必要的敏感信息，优先记录结构化枚举和流程节点。
